# CarMonitor for iOS (version 1) — design

Date: 2026-11-26. Approved approach: a separate Swift app (option 1), Android untouched.

## Why
The user's car adapter is a cheap Amazon "OBD2 BT" ELM327 clone. iPhone OBD apps reach it over Bluetooth LE, so
CarMonitor can too. Goal: log drives on an iPhone and send them to the CarMonitor Home Assistant integration exactly
as the Android app does, installed locally with AltStore.

## Goals
- Connect to BLE ELM327 clones with no pairing: auto-detect the serial service (FFF0: notify FFF1 / write FFF2;
  FFE0: FFE1 both; 18F0: notify 2AF0 / write 2AF1; else the first service with one notify and one write characteristic).
- Same vehicle model as Android: OBDb signalsets (bundled SAEJ1979 + the vehicle's set downloaded from OBDb), year filter.
- Same safety: an identical read-only RequestGuard. One shared vector file (`spec/guard-vectors.json`) is checked by
  both the Kotlin SelfTest and the Swift tests.
- Quick discovery on first connect (each command probed once, unsupported ones dropped), cached per VIN.
- Polling with fast / medium / slow tiers, multi-PID batching for service 01, CSV drive logs in the Android format
  (`ts_ms,key,signal,value,raw`, file `drive-YYYYMMDD-HHMMSS.csv`), GPS rows (GPS_LAT, GPS_LON, GPS_ACC_M).
- Upload to the integration webhook with the Android behaviour: CSV is the queue, `.sent` byte offsets, backlog
  after dropouts, `have` check to skip drives HA already has, defs (name, unit, expire), status online/offline,
  Upload drives button, Connected status.
- Background: keeps logging with the screen off (bluetooth-central + location background modes). Auto start: a pending
  BLE connect to the remembered adapter, so iOS wakes the app when the car's adapter powers up.
- Webhook URL stored in the Keychain.
- CI builds an unsigned `CarMonitor.ipa` on a macOS runner and attaches it to tag releases; AltStore signs on install.

## Non-goals (v1)
MQTT and HA-token modes, discovery sweep, overlays, poll-plan import, fuel/trip derived values, CarPlay (impossible
when sideloaded), Android Auto equivalents.

## Anti-goals
Anything that sends a non-read-only request. Any change in the Android app's behaviour.

## Constraints
- iOS 17+, Swift 6, SwiftUI, no third-party dependencies.
- Core logic in a Swift package (`ios/CarMonitorKit`) testable with `swift test` on macOS; the app target in
  `ios/CarMonitor` generated by XcodeGen (`ios/project.yml`).
- Bundled OBDb files are referenced from `app/src/main/assets/obdb/`, not copied.
- README and wiki stay car-agnostic.

## Approaches
1. Swift app with shared guard vectors (chosen): fast, isolated from the working Android app; the guard exists twice
   but both copies must pass the same vectors.
2. Kotlin Multiplatform core: one guard, but a refactor of the Android core and about 2 more days.

## Left to the builder
Screen layout details (mock up first), scheduler internals, retry timings.
